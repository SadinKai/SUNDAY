## 3. Current production architecture

Critical path:

1. Tauri Rust shell owns the window, single-app-instance behavior, native clipboard, login WebView, and the private Node child lifecycle.
2. Rust and the Node backend communicate through completion-correlated line-delimited RPC over private stdin/stdout.
3. `tauri-backend.js` owns API validation, feature gates, service composition, event emission, and shutdown ordering.
4. `LaunchCoordinator` persists plans transactionally and is the only product-level launch/stop/restart state machine.
5. `LegacyRobloxIsolationAdapter` is selected only in explicit legacy compatibility mode and owns clone allocation, singleton compatibility, exact launch evidence, process capabilities, recovery, and release.
6. `ProcessCapabilityRegistry` binds authority to PID, process creation identity, canonical executable path, file identity, owner, action set, and expiry.
7. `StateDatabase` is the shared SQLite persistence primitive for plans, leases, account records, and migrations.
8. Renderer state is split across model/core/view/action modules. Network work stays in the backend behind bounded HTTPS policies.
9. The custom Rust installer uses a closed-world payload manifest and ledger-bound removal. It does not recursively delete an install root.

The Phase 6 environment broker remains provider-neutral foundation code. The production v1.8.18 runtime selects the legacy adapter; synthetic provider qualification is not Roblox qualification.

## 5. Renderer selection lifecycle

The original failure was independent of the singleton guard.

The final renderer lifecycle is:

1. A+B are selected and submitted.
2. A successful response contains per-account results.
3. `applyLaunchSelectionResult()` calls `selectionAfterLaunch()` and removes only results with `ok === true`.
4. After the A+B `COMPLETED` response, `state.selected` is empty.
5. Active-client refresh does not repopulate selection.
6. Account refresh only prunes missing IDs and does not repopulate selection.
7. Attempting to select already-active A is rejected.
8. Before selecting C, `state.selected` is empty.
9. Selecting C creates a plan containing only C.

Packaged trace:

`A+B selected -> A+B completed [] -> active refresh [] -> account refresh [] -> active A rejected [] -> C selected [C]`

The deterministic regression also continues through C completion, refresh, D-only selection, and D completion. The recorded backend call sequence is exactly `[[A,B],[C],[D]]`.

Evidence:

- `test/six-client-capacity.test.js`: `renderer clears completed A+B through refreshes and the next plan contains only C`.
- `scripts/qualify-packaged-renderer-selection.mjs`.
- `artifacts/packaged-renderer-selection-v1.8.18.json`.

## 6. Singleton guard reconciliation

### Why it became the reported blocker

The earlier singleton implementation treated ownership of both Roblox global names as a preflight requirement. A normally running Roblox client already owns `ROBLOX_singletonMutex`; therefore a new SUNDAY process could open the mutex handle but could not acquire it. Preflight reported the guard as unavailable before launch. This was a separate launch blocker that appeared after the renderer selection problem had already been identified. It did not cause or explain stale `state.selected`.

### Exact current behavior

- `ROBLOX_singletonEvent` is reserved by creating a mutex with that exact name. This is an intentional Windows object-type squat: Roblox cannot create/open an Event under a name currently occupied by a Mutex.
- `singletonGuardReady()` requires only the event-name type squat.
- `ROBLOX_singletonMutex` is no longer a required reservation. The code still opens/creates it and may acquire it opportunistically when free, but a live external owner's contested mutex does not block launch readiness.
- Cross-process compatibility cleanup enumerates internally discovered Roblox PIDs and closes only handles proven to be the exact `ROBLOX_singletonEvent` Event handle.
- The mutex handle is not closed in another process.
- Already-running Roblox clients remain external. They are recorded for diagnostics but are not adopted into SUNDAY ownership.
- No foreign Roblox process is terminated. Broad kill-all and broad cleanup commands remain disabled.
- A process capability is minted only after SUNDAY launches a child and verifies its exact process identity and executable evidence.
- The singleton mechanism is compatible with slot clones: the global event-name compatibility guard prevents Roblox's singleton wait, while each clone retains separate slot ownership, executable path evidence, account identity, and process capability.

## 8. Performance findings

Measured bottlenecks were startup hydration, duplicate network work, cache misses, and blocking navigation states. The changes preserve the current design while making content available progressively.

Implemented:

- Launch shell paints before strict Roblox discovery and complete hydration.
- Games caches are bounded by TTL and size, share in-flight requests, and protect commits by generation.
- People/Friends caches share work and now invalidate correctly.
- Navigation renders a stable shell immediately while data finishes.
- Packaged profiler measures cold/warm Launch, Accounts, People, Friends, and Games plus boot RPC latency.

## 9. Security and privacy assessment

Verified:

- Account credential protection fails closed through DPAPI; there is no plaintext fallback.
- Login uses a per-session WebView profile, exact `https://www.roblox.com:443` navigation, cookie purge, and no renderer-visible cookie value.
- HTTP is HTTPS-only with host allowlists, redirect revalidation, body bounds, timeout, retry policy, and response-body cancellation.
- Host launch plans reject credential-, ticket-, secret-, auth-, and deep-link-shaped fields.
- Process control is capability-bound and not PID-only.
- PID reuse, executable replacement, owner mismatch, file-identity mismatch, and capability expiry fail closed.
- Foreign processes are not adopted or broadly terminated.
- Diagnostics and release audits suppress credential-like values.
- Source secret scan passed for 191 files; final portable scan passed for 359 inspected files.
- `npm audit` found 0 vulnerabilities across 13 dependencies.

Residual security boundary:

- SUNDAY-authored executables are unsigned, so local hashes establish integrity but not publisher identity.
- The bundled Node runtime has a valid OpenJS Foundation signature.
- The legacy clone/singleton adapter intentionally uses powerful Windows primitives behind explicit legacy mode. Exact live qualification remains mandatory after Roblox or Windows behavior changes.

## 15. Remaining risks and release recommendation

What still worries me:

- Legacy multi-instance behavior depends on Roblox's current global-object and executable behavior. Static and synthetic evidence cannot substitute for a controlled real-client run.
- A Windows/Roblox update, antivirus lock, or permission boundary may expose timing not reproduced by synthetic children.
- Phase 6 provider allocation-abort recovery is foundation code without a production provider; it should gain a bounded destruction/recovery contract before activation.
- Normal Rust-to-Node commands deliberately have no generic shell timeout because abandoning a live mutation can make retries unsafe. Each long operation must therefore retain its own bounded cancellation contract.
- Unsigned SUNDAY binaries will produce weaker Windows trust and reputation behavior than a signed release.

Recommendation: hold publication. The source-built candidate is suitable for the next controlled live qualification, not yet for broad release.
